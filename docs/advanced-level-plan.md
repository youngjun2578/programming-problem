## 1. 현재 구조

### 1.1 난이도 구조
- **[확인]** 난이도 값이 있다. `server/engine/types.ts`의 `Difficulty = 1 | 2 | 3`, 템플릿마다 `difficulty`를 하나 갖는다.

### 1.2 생성 → 채점 → 해설 흐름
1. `POST /api/session` → `api/session.ts` → `server/handlers.ts` `handleSession`
   - `newPublicSeed()`로 공개 시드를 만들고, `generationSeed(secret, s)`(HMAC, `server/token.ts`)로 생성 시드를 만든다.
   - `generateQuestions`(`server/diagnosis.ts`) → `generateSet`(`server/engine/set.ts`) → `makeProblem` → 템플릿 `generate` + `buildChoices`(`server/engine/choices.ts`)
   - 응답: `issueToken`으로 서명한 토큰 `{v, s, iat}`와 `toPublicQuestion`(정답·해설·난이도 제외)
   - **[확인]** 요청 본문은 읽지 않는다.
2. `POST /api/report` → `handleReport`
   - 입력 검사 → `verifyToken` → (이용권 스위치) `resolveScope` → 같은 생성 시드로 문항을 다시 만든다 → `score` → `analyze`(`server/report/analyze.ts`) → `composeReportResponse`
3. 해설은 템플릿의 `steps`이고, `composeAll`에서 문항별로 담긴다.

## 2. 설계안

### 2.1 선택 방식

| | (가) 첫 화면에서 기본/심화 선택 | (나) 기본을 마친 뒤 심화로 이어 가기 |
| --- | --- | --- |
| 장점 | 진입이 빠름. 실력 있는 사용자가 바로 심화로 감 | 기본 결과를 보고 들어가므로 대상이 맞음. 첫 화면이 지금과 같음 |
| 단점 | 첫 화면 구성이 바뀜. 처음 온 사람이 너무 어려운 쪽을 고를 수 있음 | 심화만 원하는 사람은 기본을 한 번 거쳐야 함 |
| 꺼짐 상태 영향 | 첫 화면 HTML 분기 필요 | 결과 화면에 버튼 하나(빌드 분기) |

**추천: (나)를 기본으로 한다.**
- 결과 화면에 "심화로 다시 진단" 버튼을 둔다. 전체가 안정이거나 정답률이 높을 때 강조한다.
- 같은 화면을 주소 `/diagnosis/?level=advanced`로도 열 수 있게 한다.
- 첫 화면에는 넣지 않는다. 바꾸는 곳이 가장 적고, "진단" 성격에 맞다.
- 반응을 본 뒤 필요하면 첫 화면에 보조 링크를 더한다.

### 2.2 API 호환과 level 처리
- **요청:** `POST /api/session` 본문에 `{ "level": "advanced" }`를 선택적으로 받는다.
  - 본문이 없거나 `{}`이거나 값이 다르면 기본(`basic`)이다. 기존 클라이언트는 `{}`를 보내므로 그대로 기본이다.
  - 서버 스위치(아래 2.6)가 꺼져 있으면 level을 무시하고 항상 기본이다.
- **토큰:**
  - 본문에 `l` 필드를 **심화일 때만** 넣는다: `{v:1, s, iat, l:"adv"}`.
  - 기본 토큰은 지금과 바이트 단위로 같은 모양이다. 이미 발급된 토큰도 유효하다.
  - `verifyToken`은 `l`이 없으면 기본, `"adv"`면 심화, 그 밖의 값이면 `invalid_token`.
- **생성 시드:** 심화는 다른 이름표로 만든다.
  - `generationSeed(secret, s, 'adv')` → HMAC 입력 `gen:v1:adv:${s}`
  - 기본은 지금 문자열(`gen:v1:${s}`) 그대로라서 골든 비교가 그대로 통과한다.
  - 같은 공개 시드로 기본과 심화 문제를 서로 재현할 수 없다.
- **클라이언트 말을 믿지 않기:** `/api/report`는 요청 본문의 level을 **읽지 않는다.** level은 서명이 확인된 토큰에서만 꺼낸다. 토큰 본문을 고치면 서명 검증에서 실패한다(기존 방식).
- **문항 수:** 심화도 영역당 3문항, 12문항으로 같게 둔다. 그래야 `checkReportInput`과 결과 화면 구조를 바꾸지 않는다. **[가정]** 심화 문항 수를 다르게 하려면 `QUESTION_COUNT`를 level별로 나눠야 한다.

### 2.3 기본 결과와 심화 결과를 섞지 않기
- **[확인]** 결과는 서버에 저장하지 않는다. 그래서 섞일 수 있는 곳은 화면·인쇄물·브라우저 저장소 정도다.
- **응답:** 심화일 때만 `meta.level: "advanced"`를 넣는다. 기본 응답은 필드도 지금과 같다(골든 유지).
- **화면·인쇄:** 결과 제목과 인쇄/PDF 머리에 "심화" 표시를 넣는다. 요약 표 위에 "심화 기준으로 판정했습니다"를 둔다.
- **점수 해석:** 판정 규칙(전부/60%)은 같게 두고 **권장 시간만 심화용으로 따로** 둔다(`areas.ts`에 `targetSecAdvanced`).
  - **[가정]** 숫자 예: 기초연산·기초통계 120초, 도표분석·도표작성 150초. 실제 풀이 시간을 재 본 값이 아니다.
  - **[결정 필요]** 판정 문구를 심화용으로 따로 쓸지(예: 집중 필요 → "심화에서는 흔한 결과입니다" 같은 완화 문구)
- **학습 순서:** `studyOrder`는 기본 유형 이름으로 되어 있으므로, 심화 유형은 대응하는 기본 유형 뒤에 붙인 심화용 목록을 둔다.
- **무료 1회 표시:** 지금 localStorage 키(`ncs-free-diagnosis-used`)는 하나다. 심화를 따로 셀지는 이용권 정책(2.7)에 따라 정한다.

- **구현 원칙:** 기존 템플릿 파일은 고치지 않는다. 확장분은 새 파일로 만들고, 필요한 계산 도우미만 공유한다. 기존 템플릿의 난수 호출 순서가 바뀌면 기존 문제가 달라지기 때문이다(골든이 잡아냄).

### 2.5 검증 계획
새 스크립트를 두 개 둔다. 둘 다 `npm run build`에 넣는 것을 제안한다.

1. **`scripts/validate-advanced.ts`** (`npm run validate:advanced`): `validate.ts`의 검사를 심화 템플릿에 그대로 적용하고 다음을 더한다.
   - 템플릿마다 시드 20,000개
   - **정답 유일성:**
     - 보기 문자열 중복 없음
     - 오답 값이 정답과 수치로 같지 않음(예: 0.5와 1/2, 48과 48.0)
     - 진술형(#10)은 각 진술의 참·거짓을 따로 계산해 정답 조합이 정확히 하나인지 확인
   - **자릿수·단위 일관성:** 보기 5개가 같은 단위·같은 자릿수 규칙(예: 소수 첫째 자리)을 따르는지, 정답이 반올림 경계(x.x5)에 걸리지 않는지
   - **해설 숫자 일치:** 해설에 정답 값이 나오는지(기존 검사)에 더해, 해설의 마지막 계산식 결과가 정답과 같은지
   - **재현성:** 같은 시드로 두 번 생성해 문제·보기·도표·해설이 완전히 같은지
   - **세트 단위(5,000개):** 영역별 3문항, 유형 중복 없음, 확장·신규 섞임, 문장 중복 없음
2. **`scripts/advanced-recheck.ts`** (`npm run test:advanced`): 템플릿마다 **독립 풀이 함수**를 둔다. 가이드 예제 검산(`scripts/guides/examples.ts`)과 같은 방식이다.
   - 문제 문장과 도표에서 수를 읽어 다시 풀고, 정답 보기와 대조한다(시드 수천 개).
   - 생성 코드와 풀이 코드를 따로 써야 둘이 같은 실수를 하는 것을 막을 수 있다.
3. **기존 검사 유지:**
   - `test:golden`이 그대로 통과하면 기존 문제가 바뀌지 않았다는 뜻이다.
   - 심화용 골든 파일(`tests/golden/advanced.jsonl.gz`)을 별도로 만든다.
   - `test:api`에 다음을 추가한다.
     - level 없음 → 기본
     - 잘못된 level 값 → 기본
     - 토큰 `l` 조작 → 401
     - 서버 스위치 꺼짐 → level 무시
     - 심화 토큰으로 채점

### 2.6 빌드 스위치
- **클라이언트:** `VITE_ADVANCED_LEVEL_ENABLED` (기본 꺼짐). `"true"`일 때만 심화 버튼·문구·코드를 넣는다. 지금 `VITE_MONETIZATION_ENABLED`처럼 HTML은 `<!--#if advanced-->` 분기, JS는 조건부 동적 import를 쓴다.
- **서버:** `ADVANCED_LEVEL_ENABLED` (기본 꺼짐). 꺼져 있으면 `/api/session`이 level을 무시하고, 심화 토큰(`l:"adv"`)도 거부한다. 사람이 직접 요청을 보내도 심화가 나오지 않게 하기 위해서다.
- **Production 평가:** 두 값이 없으면 다음 이유로 지금과 같다고 본다.
  - (1) 기본 세션의 요청·토큰·생성 시드·응답이 그대로다(골든·API 시험으로 확인 가능).
  - (2) 꺼진 빌드의 dist는 이전 커밋과 같아야 한다(`diff -r`로 확인. 이용권 때와 같은 방법).
  - 단, 심화 템플릿 코드는 서버 번들(Vercel 함수)에 포함된다. 실행되지 않을 뿐이다.

### 2.10 예상 위험
- **기존 문제 변경:** 공용 계산 도우미를 고치다 기존 템플릿의 난수 호출 순서가 바뀔 수 있다. 대응: 기존 파일을 고치지 않고 골든으로 확인한다.
- **진술형(#10) 정답 유일성:** 진술 4개의 참·거짓이 예상과 다르게 겹칠 수 있다. 대응: 진술별 독립 판정 후 조합을 검사하고, 실패하면 재생성한다.
- **도표 문항 생성 실패율:** 조건이 많으면 "보기 5개 구성 실패"가 늘 수 있다. 대응: 실패율을 `validate`에서 감시하고 상한을 정한다.
- **풀이 시간 기준:** 권장 시간은 **[가정]**이라, 판정이 지나치게 엄하거나 느슨할 수 있다. 공개 전에 직접 풀어 보며 조정해야 한다.
- **화면 길이:** 심화 문제 문장과 표가 길어 320px 화면에서 넘칠 수 있다. 대응: 기존 화면 점검 스크립트를 심화 세트로도 돌린다.
- **빌드 시간:** 검사 횟수가 늘어 build가 느려진다. 대응: 기본값은 적게, 정기 점검 때 크게 돌린다.
- **결과 혼동:** 기본·심화 결과를 인쇄해 나란히 볼 때 헷갈릴 수 있다. 대응: 인쇄물 머리에 표시하고, 판정 문구에 기준을 명시한다.

## 4. 구현 현황 (1차, 서버·엔진·검증)
- **한 단계:** 0, 1, 2, 3(1차분), 4. 화면 작업인 5단계부터는 하지 않았다.
- **커밋 순서:** 0 → 2·3 → 1·4. 1단계의 세션 처리가 심화 문항 생성(2단계)에 기대므로 엔진을 먼저 만들었다.
- **설계와 달라진 점**
  - 잘못된 level 값(모르는 문자열, 숫자, null, 배열)은 기본으로 바꾸지 않고 400 `bad_request`로 응답한다. 설계(2.2)는 기본 처리였다. 오타가 조용히 기본 문제로 바뀌면 심화를 요청한 화면이 기본 문제를 받게 되므로 바꿨다. level 키가 없거나, 본문이 없거나, JSON이 아니면 이전과 같이 기본이다.
  - 서버 스위치가 꺼진 상태에서 심화를 요청하면 403 `level_unavailable`이다. 스위치를 끈 뒤 남아 있는 심화 토큰으로 채점해도 같은 오류다.
- **템플릿:** 영역마다 4개, 모두 16개다(확장 7, 신규 9). 진술 조합(#10)과 두 표 결합(#9)은 2차로 미뤘다. 1차 목록은 `server/advanced/registry.ts`에 있다.
- **검증:**
  - `npm run validate:advanced`: 템플릿마다 시드 20,000개, 세트 5,000개. `npm run build`에는 `--quick`(시드 2,000개, 세트 1,000개)으로 들어간다.
  - `npm run test:advanced`: 독립 풀이로 정답을 대조한다.
  - `npm run test:golden:advanced`: 심화 골든과 비교한다.
- **권장 시간:** `server/advanced/constants.ts`에 있다. [사용자 결정 10/6: 심화 1문항 90초]로 확정했다(4.4).
- **이용권과 결과 범위:** 심화 이용 여부는 `server/levels.ts`의 `advancedAccess`에서만 판단한다(지금은 정책 A). 결과 범위(무료/이용권)는 기본과 같은 규칙(`MONETIZATION_ENABLED`)을 따른다. 심화 결과를 이용권 없이도 전부 보여 줄지는 결정이 필요하다.

### 4.1 보강 (약한 신규 템플릿 5개, 검산기)
- **이유:** 난이도 점검에서 기본 유형과 풀이 단계가 비슷하게 나온 신규 템플릿 5개에 단계나 겹치는 조건을 더했다. 템플릿 id, 난이도 값, 등록 순서, 세트 구성 규칙은 그대로다.
  - `profitChain`: 일부는 정가, 나머지는 할인가로 판 뒤 전체 이익률·이익금. 해설 4.0 → 6.5줄
  - `indexGrowth`: 중간에 기준 연도가 바뀐 지수를 같은 기준으로 맞춘 뒤 증가율. 4.0 → 5.0줄
  - `groupMean`: 세 집단의 전체 평균에서 모르는 집단 총점을 구하고, 일부 인원이 옮긴 뒤의 평균. 3.0 → 6.0줄
  - `gapBar`: 두 계열의 차이를 구한 뒤 그 전년 대비 증가량을 막대그래프로. 막대그래프가 0부터 그리므로 증가량이 모두 양수인 범위에서 고른다. 3.0 → 5.0줄
  - `perCapitaLine`: 1인당 금액의 전년 대비 증가율(%)을 꺾은선그래프로. 3.0 → 5.0줄
- **검산기:** `scripts/advanced-samples.ts --check`가 단위가 붙은 식("10억 원 ÷ 50천 명 = 0.2")과 분수 식("3/8 × 2/7 × 5/6 = 30/336")도 계산한다. 분수 결과는 정확히 같아야 맞다. `--self-test`로 맞는 식 7줄은 통과, 틀린 식 7줄은 실패로 잡는지 확인한다.
- **골든이 바뀐 이유:** 심화 세트는 난수열 하나를 12문항이 같이 쓴다. 보강한 5개 템플릿은 난수를 쓰는 횟수가 달라졌으므로, 그 뒤의 템플릿 선택과 문항이 함께 밀린다. 골든 시드 40개 중 38개에서 세트 구성이 바뀌었고, 다른 11개 템플릿 문항 297개 중 295개가 달라졌다. 다른 템플릿 코드와 세트 생성기·채점 코드는 바뀌지 않았다.
- **대체 증명(난수 위치 고정):** 갱신 전에 저장소 밖 스크립트로 다음을 확인했다.
  - 세트 생성 규칙을 복제한 생성기가 옛 코드·새 코드의 실제 생성기와 시드 340개에서 같다.
  - 혼합 세트(보강 5개 자리에서는 옛 코드로 난수를 쓰고, 새 문항은 같은 시작 상태로 만듦) 40개: 템플릿 구성·순서가 옛 골든과 모두 같고, 다른 11개 템플릿 문항 297개가 완전히 같다. `fixRecord` 33문항은 '했었다' → '했다'만 다르다.
  - 실제 새 세트 2,040개(골든 시드 40개 포함)의 문항을 그 문항 직전 난수 상태에서 옛 코드로 다시 만들면, 다른 11개 템플릿 문항 15,286개가 모두 같고 `fixRecord` 1,503문항은 문구만 다르다.
  - 음성 시험: 다른 템플릿의 숫자·보기 순서·해설·난수 소비, `fixRecord`의 숫자·태그를 일부러 바꾸면 모두 실패로 잡는다(6종). 보강 템플릿 자신의 난수 소비 변화는 이 증명이 걸러 내도록 설계한 부분이라 잡지 않는다.
  - 보강 5개의 새 정답은 `test:advanced` 독립 풀이(템플릿마다 3,000개)와 모두 맞는다.

### 4.2 난이도 값 조정과 문항별 독립 난수
- **난이도 값:** `profitChain`과 `groupMean`을 1 → 2로 바꿨다(4.1 보강으로 해설이 6줄 이상, 겹치는 조건 3개). 다른 템플릿 값은 그대로다.
  - 난이도는 세트에서 영역 안 문항 순서(오름차순)에만 쓰인다. 어떤 템플릿을 고를지는 바뀌지 않는다.
  - 영역별 난이도 값: 기초연산 2·3·3·**2**(이전 1), 기초통계 3·2·**2**(이전 1)·2. 도표분석·도표작성은 그대로다.
  - 시드 20,000개 기준 영역 안 난이도 구성
    - 기초연산: 1-2-3 67.0%, 1-3-3 33.0% → 2-2-3 67.0%, 2-3-3 33.0%
    - 기초통계: 1-2-2 25.1%, 1-2-3 49.7%, 2-2-3 25.2% → 2-2-2 25.1%, 2-2-3 74.9%
  - 자리: `profitChain`은 늘 영역 첫 문항이었으나 첫째 83.6%, 둘째 16.4%가 됐다. `groupMean`은 첫째 50.1%, 둘째 33.1%, 셋째 16.8%가 됐다. 같은 난이도끼리는 고른 순서를 따른다.
- **문항별 독립 난수(`server/advanced/seed.ts`, `server/advanced/set.ts`):** 세트 시드 하나에서 용도마다 다른 하위 시드를 만든다. 템플릿 고르기는 'pick', 자리 0~11의 문항은 'item:자리'를 쓴다. 문항 안의 다시 뽑기도 그 자리 난수만 쓴다.
  - 그래서 템플릿 하나가 난수를 몇 번 쓰든 세트 구성과 다른 자리 문항이 바뀌지 않는다.
  - 생성 시드 문자열(`gen:v1:adv:…`), 토큰 형식, 기본 세트 생성기, 채점 코드는 그대로다. 기본 골든은 바뀌지 않았다.
  - 세트 안 같은 문장 다시 뽑기 규칙은 남겼다. 한 세트의 템플릿은 모두 서로 달라 실제로 겹치지 않는다. 아래 검사에서 세트 안 문항이 모두 단독으로 만든 문항과 같았다(24,000/24,000).
- **독립성 검사(`npm run test:advanced:independence`, build에는 `--quick`):** 템플릿 하나의 난수 소비를 바꾼 시험 버전 3가지(앞에 더 쓰기, 뒤에 더 쓰기, 첫 시도 실패)를 16개 템플릿마다 만들어 시드 2,000개로 비교했다.
  - 세트 구성·순서는 96,000/96,000 같았다.
  - 다른 템플릿 문항은 1,080,000개가 같았고, 다른 문항은 0개였다.
  - 시험 버전 쪽 문항은 실제로 달라졌다(앞 23,623/24,000, 뒤 23,874/24,000, 재시도 23,548/24,000). 남는 것은 선택지가 적어 우연히 같은 문항이 나온 경우다.
  - 옛 방식(세트 전체가 난수 하나를 같이 씀)에 같은 시험을 하면, 바꾼 템플릿 뒤에 문항이 있는 세트 2,200개 중 2,033개(92.4%)에서 차이를 잡는다. 나머지는 다시 뽑기를 많이 하는 템플릿이 난수열의 같은 위치로 되돌아온(재동기화) 경우다.
- **골든 갱신:** 시드→문제 대응이 모두 바뀌었다(심화는 공개 전). 골든 시드 40개가 새 생성기 출력과 같고 독립성 검사가 통과한 것을 근거로 갱신했다.
- **샘플 문서:** 템플릿마다 `makeProblem(템플릿, new Rng(시드))`로 직접 만들어 세트 생성기를 거치지 않는다. 그래서 문제는 그대로이고 A04·A07의 난이도 표시만 2로 바뀌었다.

### 4.3 화면 5단계 (심화 진입·안내·결과 표시)
- **스위치:** 화면 스위치 `VITE_ADVANCED_LEVEL_ENABLED=true`로 빌드했을 때만 `src/ui/advanced.ts`(와 `src/styles/advanced.css`)를 동적으로 불러온다.
  - 이용권 기능과 같은 방식으로, 조건을 import 자리에 직접 써서 꺼진 빌드에서는 모듈이 통째로 빠진다.
  - 꺼진 빌드의 dist는 main(`ad2f33f`)의 꺼진 dist와 `diff -rq`로 완전히 같다(608개 파일).
- **진입**
  - 주소 `/diagnosis/?level=advanced`: 값이 정확히 `advanced`일 때만 심화를 요청한다. `xyz`, `ADVANCED`, `advanced ` 같은 값과 값이 없을 때는 기본이다. 화면 스위치가 꺼져 있으면 level을 무시한다.
  - 기본 결과 화면의 "심화로 다시 진단" 버튼: 누르면 주소에 `?level=advanced`를 남기고(history.replaceState) 심화로 시작한다.
  - 심화 결과의 "새 문제로 진단"은 다시 심화로 시작한다.
- **서버가 막을 때(403 `level_unavailable`)**
  - 세션 요청과 채점 요청 모두, 오류 화면 대신 아래 안내를 보여 준다.
    - 제목: "심화 난이도는 아직 준비 중입니다"
    - 안내: "지금은 기본 난이도로만 진단할 수 있습니다. 기본 진단은 바로 시작할 수 있습니다."
    - 버튼: "기본으로 진단하기", "홈으로"
  - "기본으로 진단하기"를 누르면 주소에서 level을 지우고 기본으로 시작한다.
- **결과·인쇄 표시:** 서버 응답의 `meta.level`(서명된 토큰에서 나온 값)이 `advanced`일 때만 넣는다. 주소는 보지 않는다.
  - 제목 옆 "심화" 표시
  - 안내 한 줄 "심화 난이도 결과입니다. 기본 결과와 직접 비교하지 않습니다."
  - 둘 다 인쇄에도 나온다.
- **이용권:** 서버 규칙이 기본과 같으므로 화면도 같은 코드를 쓴다(요약과 해설 1·2번 무료, 나머지 이용권). 무료 1회는 기본·심화 합산이며, 같은 키 `ncs-free-diagnosis-used`를 쓴다. 새 저장 항목은 없다.
- **시간 안내:** 화면이 새 시간 문구를 만들지 않는다. 영역 상세의 "권장 N초 이내"는 서버 값(`targetSec`)을 그대로 보여 준다.
  - 심화에서는 이 값이 [가정] 120·150초였으나, 4.4에서 [사용자 결정] 90초로 정했다.
- **test:api 모드 분리:** `scripts/api-test.ts`가 `MONETIZATION_ENABLED`에 따라 기준을 고른다.
  - 꺼짐 모드는 이전 기준 그대로이고 152개가 통과한다.
  - 켜짐 모드에서는 로그인 없는 채점 응답이 무료 범위(`gated: true`, 요약 4, 상세 0, 해설 2)인지 확인하며 152개가 통과한다.
  - 이전에 켜짐에서 실패하던 3건은 모두 "스위치 꺼짐"을 전제로 쓴 테스트였다. 실제 동작은 무료 범위 설계와 같다.

### 4.4 심화 권장 시간 90초 ([사용자 결정 10/6: 심화 1문항 90초])
- **결정:** 심화 1문항당 권장 시간은 네 영역 모두 90초다. 영준님이 Preview에서 직접 풀어 본 체감 기준이다. 기본(basic) 시간(75·75·90·90초)은 그대로다.
- **값의 뜻:** `ADVANCED_TARGET_SEC`는 영역별 "문항 1개당" 권장 시간(초)이다. 난이도별 값은 없다.
- **쓰이는 곳**
  - 결과·인쇄 화면의 영역 상세 "권장 N초 이내"
  - 판정 규칙: 영역을 모두 맞혔어도 문항당 평균 시간이 권장의 1.5배를 넘으면 '보완 필요'이고, 사유 문장에 권장 시간이 들어간다.
  - 우선순위 정렬의 마지막 기준(평균 시간 ÷ 권장 시간)
  - 샘플 문서의 "예상 풀이 시간"
- **판정 영향:** 판정 규칙은 그대로이고 기준선만 바뀐다. 모두 맞힌 영역이 '안정'으로 남는 평균 시간 상한이 바뀐다.
  - 기초연산·기초통계: 180초 → 135초
  - 도표분석·도표작성: 225초 → 135초
  - 다 맞히지 못한 영역의 판정은 시간과 관계없어서 바뀌지 않는다.
- **골든 갱신 근거(저장소 밖 증명):** 갱신 전에 다음을 확인했다.
  - 문항 40/40이 같았다.
  - 저장된 문항을 옛 시간(120·150)으로 다시 채점하면 옛 골든과 120/120 같았다.
  - 새 시간(90)으로 다시 채점하면 새 골든과 120/120 같았다.
  - 음성 시험 3가지(문항 변경, 입력 시간 변경, 다른 시간 값)는 모두 실패로 잡혔다.
  - 골든의 합성 입력에서 영역 판정 52개가 안정 → 보완 필요로 바뀌었다(도표분석 20, 도표작성 20, 기초연산 6, 기초통계 6).
